## 零、先说三个结论

**第一，你的机器比你想的能干。** 这台是 **Apple M4**（不是 Intel 款 Mac mini 4），10 核 CPU + Metal 4，PyTorch 的 MPS 后端完整可用，实测 MPS 显存上限 11.84GB。经实测，**1.5B 模型的 LoRA 微调只需 5.8GB、2.5 秒/步**，0.5B 更只需 1.88GB。原教程里那些"需要 40GB 显存"的要求，可以通过换小模型 + LoRA 全部绕开。

### ⚠️ 2026-11-20 复测修正（重要）

此前"3B 被 OOM 杀掉"的结论**不准确**，实测根因已定位：

| 场景 | 此前结论 | 真实根因 | 复测结果 |
|------|---------|---------|---------|
| PyTorch MPS 跑 3B | 内存不足被杀 | **磁盘满 + 系统内存被占满**导致加载期峰值溢出 | ✅ bf16 下完全正常，5.78GB |
| PyTorch MPS 跑 3B fp32 | 内存不足 | **真实硬件瓶颈**：fp32 权重 11.52GB 逼近 11.84GB 上限，推理时 OOM | ❌ 仍失败，这是真瓶颈 |
| MLX 跑 7B-4bit | 内存不足被杀 | **下载中断 + 加载期内存峰值叠加** | ✅ 清理后完全正常，3.99GB |
| PyTorch MPS 跑 7B fp16 | 未测 | **真实硬件瓶颈**：权重 15.2GB > 11.84GB 上限 | ❌ 装不下，需走 MLX 4bit |

**教训**：OOM 报错要先分清是"系统内存被别的进程占满"还是"模型本身超过硬件上限"。前者清理资源即可，后者只能换量化方案。

## 三、你的 8 周学习路线

### 第 1 周 · 摸清工具链（对应第 2 章）

**目标**：跑通微调-推理-部署的完整闭环。

```bash
# 1. 一键装环境
bash M4学习包/setup_m4_env.sh

# 2. 跑 LoRA 微调实验
cd M4学习包
M4_MODEL=Qwen/Qwen2.5-1.5B-Instruct ~/llm-lab/venv-m4/bin/python m4_labs.py 2
```

**重点观察**：0.5B 跑完后模型还在胡说，1.5B 已经能准确回答 LoRA 的定义。这个对比让你直观理解"模型能力与数据量的关系"——5 条数据只够让模型学会输出格式，知识正确性主要来自底座模型。

**部署环节**：原教程用 Gradio Spaces（需科学上网）。你的替代方案是本地起 Gradio：

```bash
~/llm-lab/venv-m4/bin/pip install -q gradio
~/llm-lab/venv-m4/bin/python -m gradio --version
```

用 `demo_app.py` 之类的入口脚本加载你训练好的 LoRA 权重，在浏览器里调用你的模型，完全离线。

### 第 2 周 · 提示工程的基本功（对应第 2 章）

```bash
~/llm-lab/venv-m4/bin/python m4_labs.py 1
```

脚本会用**免费网关强模型**和**本地 3B** 分别跑零样本/少样本/CoT 三种提示策略，同一题不同答——这就是"提示即实验"。

**必做实验**：把 temperature 设为 0.7，同一问题采样 5 次，统计答案出现次数最多的那个。这是自洽性（self-consistency），也是后续所有推理技巧里性价比最高的一个。

### 第 3 周 · 改写模型记忆（对应第 3 章）

```bash
~/llm-lab/venv-m4/bin/python m4_labs.py 3
```

实测输出：`rewrite_acc 编辑前 0.00 → 编辑后 1.00`，8.7 秒完成。

**必做对照**：把 `hparams/ROME/gpt2-m4.yaml` 里的 `model_name` 改成 `gpt2-xl`，再跑一次。你会看到耗时明显变长、显存占用上升——这就摸到了知识编辑的规模边界。

**思考题**：`locality_acc` 是 0.00，意味着邻近知识被破坏了。这正是知识编辑的核心难题——改一条记忆，不伤及其它记忆。

### 第 4 周 · 给 AI 内容盖戳（对应第 5 章）

```bash
~/llm-lab/venv-m4/bin/python m4_labs.py 4
```

实测输出：无水印 z-score ≈ 1.21，有水印 z-score ≈ 5.04，阈值 4.0。

**关键概念**：z-score 是水印强度的统计量。水印算法在生成时按"绿名单"偏置 logit，检测时统计命中绿名单的 token 比例，偏离随机基线的程度就是 z-score。

**延伸**：改 `gamma` 参数（绿名单比例）观察区分度变化；gamma 越大水印越强，文本质量越差。

### 第 5 周 · 让文本携带暗号（对应第 7 章）

```bash
~/llm-lab/venv-m4/bin/python m4_labs.py 5
```

实测输出：64 位比特流解码与原文**完全一致**。

**这是全书记有教学价值的一章**。它揭示了一个关键设计约束：**绿名单必须由上下文确定性派生**，否则解码方无法重建绿名单，信息就丢了。我在调试这个脚本时踩过这个坑——第一版用随机绿名单，编码正确但解码全错。

### 第 6 周 · 安全测评实战（对应第 10 章）

```bash
~/llm-lab/venv-m4/bin/python m4_labs.py 6
```

**本章有一个值得你反复琢磨的实测现象**：

> Case2（Agent 未评估影响就 `kill -9` 掉 5 个 systemd 核心进程）——本地 3B 模型的**最终判定是 unsafe（正确）**，但它的**风险分析原文开头写着 "The actions taken by the agent are generally safe"**。

结论对、理由错。这说明什么？安全测评必须**分开评估"风险识别"和"安全判断"两件事**——R-Judge 之所以设计 Oracle Test（把人工标注的风险描述喂给模型，看它能否做出正确判断），就是为了定位失败到底出在哪一环。你的模型在这个案例上就是"识别出了风险，但理由与结论自相矛盾"。

### 第 7 周 · 越狱攻击入门（对应第 6 章，简化版）

EasyJailbreak 框架已装好（`pip install easyjailbreak`）。原教程用 vicuna-13b 和 GPT-4 做攻击，你替换成本地模型：

**建议**：先读 `easyjailbreak` 的 `Selector / Mutator / Constraint / Evaluator` 四模块设计，再跑 `PAIR` 方法。**务必只在你自己的模型上做实验。**

### 第 8 周 · 蒸馏小模型（对应第 4 章，简化版）

## 三·补、7B 模型的 LoRA 微调（MLX 4bit 路径）—— 实测全流程

这是复测后**新增的能力**：之前判定"7B 不可行"，清理资源后发现走 MLX 的 4bit 量化路径完全可行。

### 为什么必须用 MLX 而不是 PyTorch

7B 的 fp16 权重是 **15.2GB**，而 MPS 可用上限只有 11.84GB——这是硬性物理限制，加载都装不下。而 MLX 的 4bit 量化版只有 **4.0GB**，给激活值和优化器状态留足了空间。

| 路径 | 权重体积 | 结果 |
|------|---------|------|
| PyTorch MPS + fp16 | 15.2 GB | ❌ 加载即被内核 OOM 杀掉 |
| PyTorch MPS + bf16 | 15.2 GB | ❌ 同上 |
| **MLX + 4bit 量化** | **4.0 GB** | ✅ 实测 3.99GB，正常训练 |

### 三步走通

**第 1 步：准备数据集（注意目录结构）**

MLX 的 `--data` 要的是**目录**，里面放 `train.jsonl` / `valid.jsonl` / `test.jsonl` 三个文件。直接传文件路径会报 `Training set not found or empty`。

```bash
mkdir -p ~/llm-lab/mlx_data
cat > ~/llm-lab/mlx_data/train.jsonl <<'EOF'
{"messages":[{"role":"user","content":"什么是LoRA微调？"},{"role":"assistant","content":"LoRA（Low-Rank Adaptation）通过在预训练模型的权重旁训练低秩矩阵来实现高效微调，大幅降低可训练参数量与显存占用。"}]}
{"messages":[{"role":"user","content":"什么是MLX？"},{"role":"assistant","content":"MLX 是 Apple 为 Apple Silicon 打造的机器学习框架，采用统一内存架构。"}]}
EOF
cp ~/llm-lab/mlx_data/train.jsonl ~/llm-lab/mlx_data/valid.jsonl
cp ~/llm-lab/mlx_data/train.jsonl ~/llm-lab/mlx_data/test.jsonl
```

**第 2 步：训练**

```bash
export HF_ENDPOINT=https://hf-mirror.com
~/llm-lab/venv-m4/bin/python -m mlx_lm lora \
  --model mlx-community/Qwen2.5-7B-Instruct-4bit \
  --train --data ~/llm-lab/mlx_data \
  --fine-tune-type lora \
  --iters 60 --batch-size 1 --num-layers 8 \
  --learning-rate 1e-5 \
  --steps-per-report 10 --max-seq-length 256 \
  --grad-checkpoint \
  --adapter-path ~/llm-lab/lora_7b
```

实测：60 步耗时 36 秒，68 tok/s，训练了 5.77M 参数（占 0.076%），loss 从 3.225 平稳降到 0.070。

**第 3 步：用 adapter 推理**

```bash
~/llm-lab/venv-m4/bin/python -c "
from mlx_lm import load, generate
model, tok = load('mlx-community/Qwen2.5-7B-Instruct-4bit',
                  adapter_path='~/llm-lab/lora_7b')
p = tok.apply_chat_template([{'role':'user','content':'什么是MLX？'}],
                             tokenize=False, add_generation_prompt=True)
print(generate(model, tok, prompt=p, max_tokens=80, verbose=False))
"
```

### ⚠️ 两个会让训练崩掉的坑

**坑 1：学习率过高直接训出 nan。** 实测对照：

| 配置 | 结果 |
|------|------|
| `--num-layers 8` + `--learning-rate 1e-4` | ❌ 第 10 步起 loss 变 **nan** |
| `--num-layers 8` + `--learning-rate 2e-5` | ✅ 正常收敛到 0.460 |
| `--num-layers 8` + `--learning-rate 1e-5` + 60步 | ✅ **收敛到 0.070，质量最佳** |

**坑 2：步数太少会重复退化。** 20 步 / 2e-5 的版本虽然 loss 降到 0.46，但生成时出现"MLX 是 Apple Silicon 的统一统一统一统一…"的重复循环。60 步 / 1e-5 的版本则完整输出了正确答案。

**结论**：小数据集上，**低学习率 + 适度步数**优于"高学习率 + 少步数"。这与常识相反，值得亲手验证一遍。

## 四、三个必须知道的坑（原教程没写的）

### 坑 1：EasyEdit 的依赖地狱

`pip install EasyEdit` 装出来的是**空壳**（只有 dist-info，没有实际代码），必须克隆源码。而源码又有 6 个隐性依赖要逐个补：

```bash
git clone https://github.com/zjunlp/EasyEdit.git && cd EasyEdit
../venv-m4/bin/pip install hydra-core omegaconf sentence-transformers higher iopath \
    fairscale gpustat timm opencv-python-headless av qwen-vl-utils matplotlib rouge zhipuai
```

**而且主包名是 `easyeditor` 不是 `easyedit`**，运行脚本时还要设 `PYTHONPATH=$PWD`。

### 坑 2：X-SIR 的三个坏点

- `requirements.txt` 里的 `stag` 在 Python 3.13 上**编译失败**——但它其实没被任何代码引用，可以直接跳过；
- `src_watermark/uw/__init__.py` 引用了**不存在的 `test.py`**，导致 `import src_watermark.uw` 直接报错。用 KGW 和 XSIR 即可，避开 UW；
- `seeding_scheme` 的值必须带版本号（`simple_1` 而非 `simple`），否则报 `Invalid seeding scheme`。

### 坑 3：MLX LoRA 的数据目录结构与参数名（新版变了）

- `--data` 必须指向**目录**（含 train/valid/test.jsonl），不能直接给 .jsonl 文件；
- 参数名是 `--data` `--num-layers` `--adapter-path`，不是旧版的 `--train-file` `--lora-layers` `--output-dir`；
- `--learning-rate` 必须 ≤ 2e-5，否则 4bit 量化训练会出 nan。

### 坑 4：Ollama 的 OpenAI 兼容端点会返回空 content

`http://127.0.0.1:11434/v1/chat/completions` 对 qwen3-8b 返回 `content: ''`，但 `/api/chat` 原生端点完全正常（16.1 tok/s）。**遇到空回复时改用原生端点**：

```bash
curl http://127.0.0.1:11434/api/chat -d '{
  "model":"qwen3-8b-v4flash:flash",
  "messages":[{"role":"user","content":"你好"}],
  "stream":false,"think":false
}'
```

## 七、关于读不下去的三章

**多模态（NExT-GPT）、GUI 智能体、RLHF** 这三章我建议你**读而不做**。理由：

1. **RLHF 的 PPO 需要同时在内存里放 actor 模型、reference 模型、reward 模型和 value head**，还要跑 rollout + 优化两套前向。M4 16GB 装不下这个组合。要理解 RLHF，读原理 + 看 `RLHF.ipynb` 的代码结构，比勉强跑出一个跑不动的实验更有价值。

2. **多模态训练需要 ImageBind + Vicuna-7B + 三个扩散模型（SD/AudioLDM/ZeroScope）**，官方配置是 A100 级别。

3. **GUI Agent 的 Qwen2-VL-7B 全参微调官方要求 3 张 80GB A100**。

   但这三章的**思想是可以单独吸收的**：多模态的"编码器-LLM-解码器"架构、GUI Agent 的"动作 + 置信度打分"设计，都是你在自己项目里能借鉴的模式。

**替代方案**：多模态能力你可以直接用 Ollama 的 `qwen3.5-9b-v4flash:flash`（支持视觉）和免费网关的 `nvidia/nemotron-3.5-super-vl:free` 来体验，不需要训练。
